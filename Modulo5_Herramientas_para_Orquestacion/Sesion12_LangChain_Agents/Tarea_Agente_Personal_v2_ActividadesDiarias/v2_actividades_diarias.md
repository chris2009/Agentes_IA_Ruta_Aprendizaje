## Qué cambia respecto a v1

Esta versión deja de ser "solo académica" y pasa a organizar el día completo del usuario, cruzando actividades pendientes (académicas y personales) con los compromisos ya agendados en Google Calendar. Cambios concretos frente a `Tarea_Agente_Personal`:

- **Renombre de la entidad de dominio**: `tareas.json` → `actividades.json`, y con él, todas las funciones y tools cambian de "tarea" a "actividad" (`_cargar_tareas`→`_cargar_actividades`, `_guardar_tareas`→`_guardar_actividades`, `_buscar_tarea`→`_buscar_actividad`, `consultar_tareas`→`consultar_actividades`, `agregar_tarea`→`agregar_actividad`). Las tools `calcular_prioridad`, `actualizar_estado`, `inspeccionar_carpeta` y `buscar_en_documentos` conservan el mismo nombre pero ahora reciben `actividad_id` en vez de `tarea_id`.
- **Nuevo campo `tipo`** en cada registro (`"academica"` o `"personal"`), ausente en v1; `curso` pasa a ser opcional y solo se muestra si está presente (`consultar_actividades` arma el detalle de curso condicionalmente).
- **Tools que desaparecen**: `guardar_plan_detallado` de v1 no existe en v2 — esta versión no tiene una tool separada para volcar a Markdown un plan redactado libremente por el modelo; solo queda `generar_plan`, que ahora sí escribe el reporte a disco pero con una lógica completamente distinta.
- **Tools nuevas**: `consultar_calendario(fecha="")` y `agendar_actividad(fecha, hora_inicio, hora_fin, resumen, descripcion="")`, ambas de integración con Google Calendar (detalladas abajo). Son la única razón de ser de esta versión frente a v1.
- **`generar_plan` cambia de firma y de algoritmo**: en v1 recibía `minutos_disponibles` (un solo número) y llenaba un bloque de tiempo secuencial sin relación con ningún calendario externo. En v2 recibe `fecha, hora_inicio, hora_fin` y arma la línea de tiempo del día completo: primero consulta los eventos reales del calendario para esa fecha, calcula los huecos libres entre `hora_inicio` y `hora_fin`, y solo dentro de esos huecos va insertando actividades pendientes por orden de urgencia — nunca sobre un bloque ya ocupado. El Markdown resultante ahora mezcla bloques `"Ocupado: {resumen del evento}"` con bloques de actividades asignadas, ordenados cronológicamente (`bloques.sort()`), a diferencia de v1 que solo listaba actividades sin huecos ni eventos externos.
- **Total de tools del agente**: v1 tenía 8 tools; v2 tiene **9** — `consultar_actividades, agregar_actividad, calcular_prioridad, actualizar_estado, consultar_calendario, agendar_actividad, generar_plan, inspeccionar_carpeta, buscar_en_documentos`.
- **Nuevas funciones auxiliares de tiempo**: `_hhmm_a_minutos(hhmm)` y `_minutos_a_hhmm(minutos)`, conversores entre el formato `"HH:MM"` legible y minutos-desde-medianoche (entero), necesarios para poder comparar y aritmética de horarios con los eventos de Calendar.
- El resto de las funciones auxiliares (`_normalizar`, `_validar_ruta`, `_puntaje_urgencia`, `_extraer_texto_archivo`, `extraer_texto`) y el mecanismo de backend intercambiable (`AGENT_MODEL`, `resolver_modelo()`) se mantienen prácticamente idénticos a v1, mismo comportamiento y mismos valores por defecto (`claude-sonnet-4-6` para Anthropic, `google/gemma-4-e4b` para LM Studio).
- El código además está reorganizado en secciones numeradas con comentarios de bloque (`# 1. CONFIGURACION`, `# 2. HELPERS COMPARTIDOS`, `# 3. GOOGLE CALENDAR`, etc.), cosa que v1 no tenía.

## Integración con Google Calendar

El acceso a Calendar usa el *scope* (permiso) `https://www.googleapis.com/auth/calendar.events`, definido en `GOOGLE_SCOPES`. Este scope permite leer y escribir **eventos**, pero el código lo usa deliberadamente de forma restringida: solo lee eventos y crea eventos nuevos, nunca edita ni borra uno existente — esto está impuesto por diseño en las tools y reforzado como regla explícita en `PROMPT_SISTEMA`, no por una restricción técnica del scope en sí (el scope sí permitiría editar/borrar si el código lo hiciera).

### `_obtener_servicio_calendario()`
Es la función central de autenticación OAuth2 (Open Authorization 2, protocolo estándar para autorizar acceso a una API sin compartir la contraseña). Intenta cargar credenciales ya guardadas desde `token.json` (`RUTA_TOKEN`); si no existen o están vencidas, intenta refrescarlas con el `refresh_token` (sin intervención del usuario); si eso tampoco es posible, dispara el flujo interactivo completo con `InstalledAppFlow.from_client_secrets_file(credentials.json)` y `flow.run_local_server(port=0)`, que abre el navegador para que el usuario inicie sesión y otorgue permiso, y levanta un servidor HTTP local temporal para recibir el callback de Google. En cualquiera de los dos últimos casos, guarda las credenciales resultantes en `token.json` para no tener que repetir el login. Si `credentials.json` no existe, lanza `FileNotFoundError` con un mensaje que remite a `CONFIGURAR_GOOGLE_CALENDAR.md`. Al final construye y devuelve el cliente de la API con `build("calendar", "v3", credentials=creds)`. Todas las tools de Calendar pasan por esta función antes de hacer cualquier llamada.

### `_obtener_eventos_dia(fecha)`
Dada una fecha (`YYYY-MM-DD`, o el día de hoy si viene vacía), arma el rango horario completo del día en la zona horaria local del sistema (`datetime.now().astimezone().tzinfo`) y llama a `servicio.events().list(...)` con `singleEvents=True` (expande eventos recurrentes en instancias individuales) y `orderBy="startTime"`. Devuelve una lista simplificada de diccionarios `{"resumen", "inicio", "fin"}`, extrayendo `dateTime` para eventos con hora puntual o `date` para eventos de todo el día (los eventos de todo el día no tienen componente horario y por eso el resto del código los distingue buscando si `"T"` está presente en el string de inicio — separador ISO 8601 entre fecha y hora).

### `_calcular_huecos_libres(hora_inicio, hora_fin, eventos)`
Algoritmo de barrido lineal: convierte `hora_inicio`/`hora_fin` a minutos con `_hhmm_a_minutos`, filtra solo los eventos con hora puntual (`"T" in e["inicio"]` — los eventos de todo el día se ignoran porque no bloquean un rango horario específico) y los ordena por inicio. Mantiene un `cursor` que arranca en `inicio_min`; por cada evento ocupado, si el evento empieza después del cursor, ese tramo intermedio es un hueco libre; luego el cursor avanza al final del evento (con `max`, para tolerar eventos solapados). Al terminar de recorrer los eventos, si sobra tiempo entre el cursor y `fin_min`, ese resto también es un hueco libre. Devuelve una lista de tuplas `(inicio, fin)` en minutos, descartando huecos de duración cero o negativa. Es la función que le permite a `generar_plan` saber dónde sí puede insertar actividades.

### `_crear_evento(fecha, hora_inicio, hora_fin, resumen, descripcion)`
Construye los objetos `datetime` de inicio y fin combinando la fecha con las horas parseadas (`datetime.strptime(hora_inicio, "%H:%M")`), en la zona horaria local, y llama a `servicio.events().insert(calendarId="primary", body={...})`. Es la única función de todo el módulo que escribe en Google Calendar; el comentario en el código lo remarca explícitamente ("No toca eventos existentes").

### Tools expuestas al agente

- **`consultar_calendario(fecha="")`**: envuelve `_obtener_eventos_dia`, capturando `FileNotFoundError` (credenciales faltantes) y cualquier otra excepción de la API para devolver mensajes de error legibles en vez de propagar la excepción hacia el loop de chat. Formatea cada evento como `"- {resumen}: {HH:MM}-{HH:MM}"` o `"- {resumen}: todo el dia"` según corresponda. El *docstring* deja claro que es de solo lectura y que debe usarse antes de proponer cualquier horario.
- **`agendar_actividad(fecha, hora_inicio, hora_fin, resumen, descripcion="")`**: envuelve `_crear_evento` con el mismo manejo de errores, y devuelve un mensaje de confirmación que incluye el `htmlLink` del evento creado (enlace directo para verlo en Google Calendar). El *docstring* es enfático: "Esta es la UNICA accion de escritura permitida" y exige confirmar fecha/hora/resumen con el usuario y consultar `consultar_calendario` antes de llamarla, para evitar agendar sobre un bloque ocupado.
- **`generar_plan(fecha, hora_inicio, hora_fin)`**: descrita en detalle en la sección anterior; internamente llama a `_obtener_eventos_dia` y `_calcular_huecos_libres` antes de distribuir las actividades pendientes (ordenadas por `_puntaje_urgencia`) dentro de cada hueco, agregando 10 minutos de descanso entre actividades cuando el hueco restante lo permite. Combina en una sola lista `bloques` tanto los tramos "Ocupado: {evento}" como las actividades asignadas, los ordena cronológicamente y genera el archivo Markdown en `planes_generados/{codigo_plan}.md`, igual que en v1.

## `autenticar_calendario.py`

Es un script de un solo uso, independiente del agente principal, cuyo único propósito es generar `token.json` la primera vez (o después de cambiar el *scope* de permisos). Es deliberadamente mínimo: no define funciones, corre secuencialmente a nivel de módulo. Carga `credentials.json` de la misma carpeta, construye el flujo OAuth con `InstalledAppFlow.from_client_secrets_file(...)` usando el mismo scope `calendar.events`, ejecuta `flow.run_local_server(port=0)` (que abre el navegador, el usuario inicia sesión y autoriza, y el script recibe el token vía un servidor local temporal), y escribe el resultado en `token.json`.

Existe como script separado — en vez de dejar que `_obtener_servicio_calendario()` del agente principal maneje el primer login — por una razón práctica documentada en el propio docstring: el login interactivo de OAuth necesita abrir un navegador y recibir un callback en `localhost`, y en WSL2 (Windows Subsystem for Linux 2, la capa de compatibilidad de Linux dentro de Windows) hay un bug conocido de reenvío de `localhost` entre WSL2 y Windows que rompe ese callback. La solución práctica es correr este script de autenticación una sola vez con el intérprete de Python nativo de Windows (no el de WSL) para generar `token.json` sin problemas de red; una vez generado, el agente principal —que sí puede correr normalmente en WSL— reutiliza ese `token.json` sin volver a necesitar el navegador. El docstring también advierte que si existía un `token.json` generado con un *scope* anterior (de solo lectura), hay que borrarlo antes de correr el script, porque Google exige un nuevo consentimiento del usuario cuando cambia el conjunto de permisos solicitado.
