# Versión 3 — Tarea_Agente_Personal_v3_Web (Sesión 12)

Carpeta documentada: `Modulo5_Herramientas_para_Orquestacion/Sesion12_LangChain_Agents/Tarea_Agente_Personal_v3_Web/` (backend FastAPI + frontend React/Vite).

## Resumen

Es la versión 2 (agente ReAct de línea de comandos con integración a Google Calendar) envuelta en una aplicación web de un solo usuario, sin autenticación ni login: un backend FastAPI (Python) expone la lógica del agente como una API (interfaz de programación de aplicaciones) HTTP, y un frontend React (con Vite como *bundler*, la herramienta que empaqueta el código para el navegador) consume esa API con varias páginas dedicadas (actividades, calendario, planes, materiales, chat). La decisión de arquitectura clave es que el backend **no duplica** la lógica de v2: importa el script `agente_planificacion_actividades.py` de v2 como si fuera una librería de Python (vía manipulación de `sys.path`), de modo que v2 sigue siendo la única fuente de verdad — sus funciones internas, sus *tools* y el propio agente compilado se reutilizan tal cual. Como consecuencia, todas las *tools* de v2 (incluida `buscar_en_documentos`, la búsqueda documental por coincidencia literal de texto, sin RAG — *Retrieval-Augmented Generation*, generación aumentada por recuperación con vectores semánticos) llegan a v3 sin cambios; el backend de v3 no las reescribe, solo las invoca.

## Backend — estructura FastAPI

### config.py y deps.py

`config.py` es el módulo que realiza la importación de v2 como librería. Calcula `V2_DIR` como la carpeta hermana `Tarea_Agente_Personal_v2_ActividadesDiarias` (subiendo dos niveles desde `config.py` con `Path(__file__).resolve().parents[2]` y navegando al directorio adyacente), y valida con un `if` que el archivo `agente_planificacion_actividades.py` exista ahí — si no, lanza `RuntimeError` con un mensaje explícito en vez de fallar más adelante con un error críptico de import.

El punto delicado, documentado en el propio *docstring* del archivo, es el orden de carga del `.env`: v2 llama `load_dotenv()` a secas dentro de su propio script, lo cual depende del directorio de trabajo (*cwd*) del proceso que lo importa — que en este caso es el proceso de v3, no el de v2. Por eso `config.py` llama `load_dotenv(V2_DIR / ".env")` **antes** de importar el módulo de v2; como `python-dotenv` no sobrescribe variables ya presentes en `os.environ` por defecto (`override=False`), cuando el `load_dotenv()` interno de v2 se ejecuta después, ya no tiene nada que cargar (es un no-op) y las variables correctas (claves de API, rutas de credenciales de Google) ya están en el entorno.

Con `sys.path.insert(0, str(V2_DIR))` seguido de `import agente_planificacion_actividades as v2mod`, Python trata la carpeta de v2 como si fuera un paquete instalado, y `v2mod` queda disponible como objeto módulo con todas sus funciones, constantes (`CARPETA_AUTORIZADA`, `CARPETA_PLANES`, `RUTA_CREDENCIALES`, etc.), *tools* (`agregar_actividad`, `actualizar_estado`, `generar_plan`, `agendar_actividad`, `buscar_en_documentos`, ...) y el `agent` ya compilado por `create_agent`. `config.py` también define `FRONTEND_ORIGINS`, la lista blanca de orígenes permitidos para CORS (`http://localhost:5173` y `http://127.0.0.1:5173`, los puertos por defecto de Vite en desarrollo).

`deps.py` es minúsculo a propósito: expone una única función `get_v2()` que devuelve `v2mod`, pensada para usarse como dependencia de FastAPI (`Depends(get_v2)`) en cada endpoint. No agrega lógica — es el punto único de acceso al módulo de v2 desde los routers, de forma que si en el futuro hiciera falta mockearlo en tests, solo hay que sobreescribir esta dependencia.

### main.py

Crea la instancia de `FastAPI` con metadatos (`title`, `description`, `version`) y un `lifespan` (contexto que se ejecuta al arrancar y apagar la aplicación, reemplazo moderno de los eventos `startup`/`shutdown`) que solo hace una verificación no bloqueante: si `v2mod.RUTA_CREDENCIALES` no existe, imprime un aviso por consola indicando que las *tools* de Calendar fallarán hasta que se configure — no impide que el servidor arranque, porque el resto de la app (actividades, planes, materiales) no depende de Google Calendar.

Registra `CORSMiddleware` (Cross-Origin Resource Sharing, el mecanismo del navegador que restringe qué orígenes pueden llamar a una API desde JavaScript) permitiendo los orígenes de `FRONTEND_ORIGINS` con todos los métodos y *headers*. Luego incluye los seis routers (`health`, `activities`, `calendar`, `plans`, `files`, `chat`), todos bajo el prefijo `/api`. Al final, un bloque `if __name__ == "__main__"` permite lanzar el servidor directamente con `uvicorn.run(..., reload=True)` para desarrollo, aunque en la práctica también puede arrancarse con el comando `uvicorn app.main:app`.

### Modelos Pydantic (models/)

Cada archivo de `models/` define los esquemas (clases `BaseModel` de Pydantic) que FastAPI usa para validar el cuerpo de las peticiones (*request*) y tipar las respuestas (*response*), sirviendo también como documentación automática en `/docs`.

- **`activities.py`**: `ActividadIn` (datos para crear una actividad: nombre, tipo restringido a `"academica"`/`"personal"` con `Literal`, fecha límite, duración, prioridad restringida a `"alta"`/`"media"`/`"baja"`, y campos opcionales de curso/ruta/entregable), `ActividadOut` (la actividad completa tal como se devuelve al frontend, incluyendo los campos calculados `puntaje_urgencia` y `dias_restantes` que no viven en el JSON de v2 sino que el router los agrega), `EstadoUpdateIn` (un `Literal` con los tres estados válidos) y `MensajeOut` (envoltorio genérico `{mensaje: str}` que usan varios endpoints de escritura para devolver el texto que ya generan las *tools* de v2).
- **`calendar.py`**: `EventoOut` (resumen/inicio/fin de un evento ya existente) y `EventoIn` (datos para crear un evento nuevo: fecha opcional, horas, resumen, descripción opcional).
- **`chat.py`**: `ChatMessage` (un turno con `role` restringido a `"user"`/`"assistant"` y `content`), `ChatRequest` (mensaje nuevo + `history` como lista de `ChatMessage`, ya que el backend no persiste conversaciones — el frontend reenvía el historial completo en cada turno) y `ChatResponse` (la respuesta del agente + el historial actualizado).
- **`files.py`**: `FileEntry` (una entrada del explorador: nombre, si es carpeta, ruta relativa, y si su extensión está admitida) y `FileBrowseOut` (la ruta actual explorada + la lista de entradas).
- **`plans.py`**: `PlanGenerateIn` (fecha opcional + rango horario para pedirle al agente que arme un plan), `PlanListItem` (nombre de archivo, fecha de generación, URL de descarga — para listar el historial de planes) y `PlanContenidoOut` (nombre de archivo + contenido Markdown completo, para la vista previa).

### Routers (routers/)

Los seis routers se dividen claramente en dos categorías: los que **leen directamente** los datos de v2 (accediendo a funciones privadas o constantes del módulo, sin pasar por el agente) y los que **escriben invocando las mismas *tools*** que usaría el agente conversacional, mediante `tool.invoke(dict_de_argumentos)` (la forma estándar de LangChain para ejecutar una *tool* decorada con `@tool` fuera del ciclo de razonamiento del modelo, pasándole directamente sus argumentos como si el LLM la hubiera "llamado"). Esto es clave conceptualmente: cuando un usuario llena el formulario "Nueva actividad" en la web, **no** pasa por el LLM — el router llama `v2.agregar_actividad.invoke(...)` directamente, ahorrando una llamada de modelo y garantizando determinismo; el LLM solo entra en juego en el router de `chat`.

- **`health.py`** (`GET /api/health`): expone un *health check* simple con el modelo de agente activo (`v2.AGENT_MODEL`) y si existen los archivos de credenciales/token de Google Calendar, útil para que el frontend (o quien despliegue el servicio) diagnostique configuración sin mirar logs.

- **`activities.py`** (prefijo `/activities`):
  - `GET ""` — lectura directa: llama `v2._cargar_actividades()` (función privada de v2 que lee `actividades.json` completo), le agrega a cada actividad los campos calculados `puntaje_urgencia` (vía `v2._puntaje_urgencia`) y `dias_restantes`, y ordena el resultado por urgencia descendente antes de devolverlo.
  - `POST ""` — escritura vía *tool*: invoca `v2.agregar_actividad.invoke(datos.model_dump())`, pasando el cuerpo validado por `ActividadIn` como diccionario de argumentos.
  - `PATCH "/{actividad_id}/estado"` — escritura vía *tool*: invoca `v2.actualizar_estado.invoke(...)`; si el mensaje de retorno de la *tool* empieza con `"No existe"` (la convención de error que usa v2, que devuelve strings en vez de lanzar excepciones), el router lo traduce a un `HTTPException` 404 real, adaptando el estilo "texto para LLM" de v2 al estilo "código de estado HTTP" que espera un cliente web.

- **`calendar.py`** (prefijo `/calendar`):
  - `GET "/events"` — lectura directa: llama `v2._obtener_eventos_dia(fecha)`, que habla con la API de Google Calendar; captura `FileNotFoundError` (credenciales ausentes) devolviendo 503, y cualquier otra excepción devolviendo 502 con el detalle, distinguiendo "no está configurado" de "falló la consulta".
  - `POST "/events"` — escritura vía *tool*: invoca `v2.agendar_actividad.invoke(datos.model_dump())`, que crea un evento real en Google Calendar (distinto de registrar una actividad pendiente en `actividades.json`).

- **`chat.py`** (`POST /chat`): es el único router que invoca el **agente completo** (no una *tool* suelta). Convierte el `history` recibido a una lista de diccionarios `{"role", "content"}`, le agrega el mensaje nuevo del usuario, y llama `await v2.agent.ainvoke({"messages": historial})` (la variante asíncrona de invocar el grafo ReAct compilado por `create_agent` en v2). El detalle no trivial está en cómo se arma la respuesta: en vez de tomar solo el último mensaje del resultado, toma **todos** los mensajes nuevos generados en ese turno (`resultado["messages"][len(historial):]`), filtra los que son de tipo `"ai"` con texto no vacío (usando `v2.extraer_texto` para normalizar el contenido, igual que en el *loop* de chat de v2), y los concatena con doble salto de línea. Esto evita perder el razonamiento intermedio del agente cuando resuelve la petición en varios pasos (por ejemplo: texto → llamada a `consultar_actividades` → más texto → llamada a `generar_plan` → texto final), que con solo el último mensaje quedaría como un fragmento suelto sin contexto.

- **`files.py`** (prefijo `/files`, endpoint `GET "/browse"`): expone un explorador de solo lectura sobre `v2.CARPETA_AUTORIZADA` (la carpeta de materiales que v2 protege contra *path traversal*). Define su propia función auxiliar `_resolver_dentro_de_carpeta_autorizada`, deliberadamente distinta de `v2._validar_ruta` (que resuelve rutas relativas al script de v2 y espera el prefijo `"materiales/"`, pensado para el campo `ruta_contexto` de una actividad) porque este endpoint usa una convención de rutas relativas distinta: la `ruta_relativa` que devuelve el propio listado, anclada a `CARPETA_AUTORIZADA`. Si la ruta pedida cae fuera de la carpeta autorizada devuelve 403; si no es un directorio, 404. Cada entrada listada indica si es carpeta y si su extensión está en `v2.EXTENSIONES_ADMITIDAS`.

- **`plans.py`** (prefijo `/plans`):
  - `POST "/generate"` — escritura vía *tool*: invoca `v2.generar_plan.invoke(datos.model_dump())`, la misma *tool* que arma el plan distribuyendo actividades pendientes en los huecos libres del calendario y lo guarda como Markdown en `CARPETA_PLANES`.
  - `GET ""` — lectura directa: lista los archivos `.md` de `v2.CARPETA_PLANES` ordenados por fecha de modificación descendente, devolviendo nombre, fecha formateada y la URL de descarga.
  - `GET "/{nombre_archivo}"` y `GET "/{nombre_archivo}/download"` — ambos pasan primero por `_validar_nombre_plan`, que resuelve la ruta y verifica que el archivo resultante quede **exactamente** dentro de `CARPETA_PLANES` (comparando `ruta.parent` contra la carpeta resuelta) y que la extensión sea `.md`, rechazando con 400 cualquier intento de *path traversal* vía el nombre de archivo; si el archivo no existe, 404. El primero devuelve el contenido como texto (para la vista previa en el frontend), el segundo lo sirve como `FileResponse` con `Content-Disposition` de descarga.

## Frontend — estructura React

### api/client.js

Es la única capa de comunicación con el backend: define `BASE_URL` (leído de la variable de entorno de Vite `VITE_API_BASE_URL`, con `http://127.0.0.1:8000` como valor por defecto para desarrollo local) y una función interna `solicitar(ruta, opciones)` que envuelve `fetch`, siempre apuntando a `${BASE_URL}/api${ruta}` con cabecera `Content-Type: application/json`. Si la respuesta no es `ok`, intenta parsear el cuerpo como JSON para extraer el campo `detail` (la convención de mensaje de error de FastAPI/`HTTPException`) y lo usa como mensaje del `Error` lanzado; si el cuerpo no es JSON parseable, usa un mensaje genérico con el código de estado. El resto del archivo son funciones específicas (`getActivities`, `createActivity`, `updateEstado`, `getEvents`, `createEvent`, `generatePlan`, `listPlans`, `getPlan`, `downloadPlanUrl`, `browseFiles`, `sendChat`, `getHealth`) que son envoltorios delgados de `solicitar` con la ruta y el método correctos — ningún componente llama `fetch` directamente, todos pasan por este módulo.

### App.jsx, main.jsx

`main.jsx` es el punto de entrada de Vite/React: monta la aplicación en el elemento `#root` dentro de `StrictMode` (modo de desarrollo que ayuda a detectar efectos secundarios impuros) envuelta en `BrowserRouter` (de `react-router-dom`, para *routing* del lado del cliente basado en la API de historial del navegador), e importa `styles/global.css` globalmente antes de renderizar `App`.

`App.jsx` define el *layout* general de toda la aplicación: un contenedor `.app-shell` con la barra lateral (`NavBar`) fija a la izquierda y un área de contenido (`.app-content` / `.app-content-inner`) que centra las páginas con ancho máximo, más un `Footer` fijo abajo fuera del `.app-shell`. El enrutamiento se declara con `<Routes>`/`<Route>` mapeando siete rutas a sus páginas: `/` → `DashboardPage`, `/actividades` → `ActivitiesPage`, `/actividades/nueva` → `NewActivityPage`, `/calendario` → `CalendarPage`, `/planes` → `PlansPage`, `/materiales` → `MaterialsPage`, `/chat` → `ChatPage`. No hay rutas protegidas ni lógica de autenticación, consistente con que esta versión es de un solo usuario implícito.

### Componentes reutilizables

- **`ActivityTable.jsx`**: tabla de actividades (nombre, tipo, curso, fecha de vencimiento con días restantes, prioridad, urgencia, estado) reutilizada tanto en el Dashboard como en la página de Actividades. Si la lista está vacía muestra un estado vacío con ícono. Cada fila tiene un botón que avanza el estado de la actividad al siguiente de un ciclo fijo (`pendiente → iniciada → completada → pendiente`, definido en el objeto `SIGUIENTE_ESTADO`), delegando la llamada real al *callback* `onCambiarEstado` que recibe por props.
- **`Banner.jsx`**: mensaje de estado en línea (error/éxito/info) con ícono según el tipo; si no recibe contenido (`children` vacío/`null`) no renderiza nada, lo que permite usarlo siempre en el JSX de una página sin condicionales adicionales (`<Banner type="error">{error}</Banner>` con `error=""` simplemente no pinta nada).
- **`ChatBubble.jsx`**: una burbuja de mensaje de chat, alineada a la derecha con avatar de usuario si `role === "user"`, a la izquierda con avatar de robot si es del asistente.
- **`FileBrowser.jsx`**: explorador de `CARPETA_AUTORIZADA` con navegación por migas de pan (*breadcrumbs*). Mantiene su propio estado de `ruta` actual y recarga el listado (vía `browseFiles`) cada vez que cambia, con manejo de carga y error propios. Tiene doble uso, controlado por si recibe la prop `onSelect`: sin ella es un explorador de solo navegación (usado en `MaterialsPage`); con ella, cada nivel muestra un botón "Elegir esta carpeta" que dispara el *callback* con la ruta actual (usado como selector embebido en `NewActivityPage` para completar el campo `ruta_contexto`).
- **`Footer.jsx`**: pie de página fijo y estático, con la atribución "Elaborado por @Sherlock".
- **`NavBar.jsx`**: la barra lateral de navegación. Define la lista de enlaces (`ENLACES`) con ícono, etiqueta y ruta, renderizados como `NavLink` (que aplican la clase `active` automáticamente en la ruta actual). Tiene estado propio de colapso (persistido en `localStorage` bajo la clave `sidebar-colapsado`) que reduce el ancho de la barra a solo íconos, y un botón de cambio de tema que delega en el *hook* `useTheme`.
- **`PlanCard.jsx`**: tarjeta de un plan generado, con nombre de archivo, fecha, un botón para mostrar/ocultar una vista previa del contenido (renderizado como Markdown vía `ReactMarkdown`, obtenido bajo demanda) y un enlace de descarga directo (`downloadPlanUrl`) apuntando al endpoint de descarga del backend.
- **`Spinner.jsx`**: indicador de carga minimalista (círculo animado por CSS) con una etiqueta de texto opcional al lado.
- **`UrgencyBadge.jsx`**: exporta dos componentes, `BadgePrioridad` y `BadgeEstado`, cada uno una etiqueta (*pill*) de color según un mapa fijo (`COLOR_PRIORIDAD`, `COLOR_ESTADO`) que asigna una clase CSS distinta por valor (alta/media/baja; pendiente/iniciada/completada).

### hooks/useTheme.js

*Hook* de React que encapsula el tema claro/oscuro: inicializa el estado leyendo `localStorage.getItem("theme")` (con `"light"` como valor por defecto), y en un `useEffect` sincroniza dos cosas cada vez que cambia: escribe el atributo `data-theme` en `document.documentElement` (que es lo que activa las variables CSS del tema oscuro definidas en `global.css`) y persiste el valor en `localStorage` para que sobreviva a recargar la página. Expone `theme` y `toggleTheme` (que alterna entre `"light"`/`"dark"`).

### Páginas

- **`DashboardPage.jsx`**: pantalla de inicio. Carga actividades con `getActivities`, filtra las que **no** están `completada`, y las muestra en `ActivityTable` ordenadas por urgencia (el orden ya viene así desde el backend). Reutiliza el mismo patrón de cambiar estado que `ActivitiesPage`.
- **`ActivitiesPage.jsx`**: listado completo de actividades (sin filtrar por estado), con un enlace a "Nueva actividad" en el encabezado. Misma lógica de carga/recarga y cambio de estado que el Dashboard, pero usando `ActivityTable` para mostrar el catálogo completo en vez del recorte de pendientes.
- **`NewActivityPage.jsx`**: formulario controlado para dar de alta una actividad (nombre, tipo, curso, fecha límite, duración, prioridad, entregable, ruta de materiales). El campo de ruta de materiales puede escribirse a mano o completarse abriendo un `FileBrowser` embebido en modo selector. Al enviar, llama `createActivity` (que internamente pega a `POST /activities`, es decir a la *tool* `agregar_actividad` de v2) y, tras mostrar el mensaje de éxito, navega automáticamente a `/actividades` después de una breve pausa (`setTimeout` de 800 ms).
- **`CalendarPage.jsx`**: combina dos funciones en una página. Arriba, un selector de fecha que dispara `getEvents(fecha)` y lista los eventos reales de Google Calendar de ese día (distinguiendo eventos con hora de eventos de todo el día según si el campo `inicio` incluye `"T"`). Abajo, un formulario para agendar un evento nuevo (`createEvent`, que llama a la *tool* `agendar_actividad`), con una nota explícita en la interfaz aclarando que esto crea un evento **real** en Google Calendar, distinto de registrar una actividad pendiente.
- **`PlansPage.jsx`**: formulario para pedir un plan nuevo (fecha + rango horario) que llama `generatePlan` (`POST /plans/generate`, la *tool* `generar_plan`), y debajo un historial de planes ya generados (`listPlans`), cada uno renderizado con `PlanCard`. La vista previa de cada plan se carga bajo demanda la primera vez que se pulsa "Ver preview" (`getPlan`) y se guarda en un diccionario de estado `previews` indexado por nombre de archivo, para no volver a pedirla si se oculta y se vuelve a mostrar.
- **`MaterialsPage.jsx`**: página mínima que solo monta `FileBrowser` en modo navegación pura (sin `onSelect`), para explorar la carpeta de materiales de forma independiente del formulario de nueva actividad.
- **`ChatPage.jsx`**: interfaz conversacional con el agente. Mantiene el `historial` completo en estado de React (no persistido: se pierde al recargar la página), agrega optimistamente el mensaje del usuario a la lista antes de que responda el backend, muestra una burbuja "Pensando…" mientras espera, y llama `sendChat(mensaje, historial)` (`POST /chat`); al recibir la respuesta, reemplaza el historial local por el `history` que devuelve el backend (que ya incluye el mensaje del usuario y la respuesta del agente), manteniendo frontend y backend sincronizados sobre una única fuente de verdad del historial en cada turno.

### Estilos (global.css)

El archivo se organiza como un sistema de diseño ligero basado en variables CSS (*design tokens*) declaradas en `:root` — colores de fondo/superficie/texto/bordes, color primario y sus variantes, colores semánticos (peligro/éxito), radios de borde, escala de espaciado (`--space-1` a `--space-6`) y dimensiones de *layout* (ancho de la barra lateral expandida/colapsada, alto del *footer*). El tema oscuro se implementa redefiniendo ese mismo conjunto de variables bajo el selector `:root[data-theme="dark"]` (activado por `useTheme`), de modo que el resto de las reglas CSS no necesita duplicarse: solo referencian las variables. A partir de ahí, el archivo se organiza en bloques comentados por área: *shell*/layout (barra lateral colapsable, contenido centrado con ancho máximo), *banners*, tarjetas/superficies genéricas, la tabla de actividades y sus insignias (*badges*) de prioridad/estado, botones (primario y "pequeño"), formularios, el explorador de archivos con migas de pan, la lista de eventos de calendario, las tarjetas de plan, el *footer* fijo, y por último los estilos específicos del chat (burbujas alineadas según el emisor, ventana con scroll interno, formulario de envío). Es CSS plano, sin *utility classes* al estilo Tailwind ni preprocesador: cada componente/página tiene su propio bloque de clases con nombres descriptivos en español/inglés mixto siguiendo el resto del código.

## Flujo de datos end-to-end (ejemplo)

Trazando el caso "el usuario genera un plan del día" desde `PlansPage`:

1. El usuario completa el formulario (fecha, hora de inicio, hora de fin) en `PlansPage.jsx` y pulsa "Generar plan". El manejador `generar` llama a `generatePlan(form)` de `api/client.js`.
2. `generatePlan` ejecuta `solicitar("/plans/generate", { method: "POST", body: JSON.stringify(datos) })`, es decir, un `POST` a `http://127.0.0.1:8000/api/plans/generate` con el JSON `{ fecha, hora_inicio, hora_fin }`.
3. En el backend, `main.py` enruta la petición al router `plans.py`. El endpoint `generar_plan(datos: PlanGenerateIn, v2=Depends(get_v2))` recibe el cuerpo ya validado por Pydantic y ejecuta `v2.generar_plan.invoke(datos.model_dump())` — no pasa por el LLM ni por `agent.invoke`, invoca directamente la *tool* de v2.
4. Dentro de v2, la función decorada `generar_plan` consulta los eventos reales del día en Google Calendar (`_obtener_eventos_dia`), calcula los huecos libres entre `hora_inicio` y `hora_fin` (`_calcular_huecos_libres`), ordena las actividades pendientes de `actividades.json` por `_puntaje_urgencia` descendente, y va asignando actividades a los huecos sin pisar los eventos ya agendados. Arma un documento Markdown con una tabla de bloques horarios, lo guarda como `CARPETA_PLANES/PLAN-{timestamp}.md`, y devuelve un string de confirmación (cuántas actividades entraron, cuántos eventos se respetaron, dónde quedó el archivo).
5. El router `plans.py` envuelve ese string en `{"mensaje": ...}` y FastAPI lo serializa como respuesta JSON con código 200.
6. De vuelta en `PlansPage.jsx`, la promesa de `generatePlan` se resuelve: el mensaje se muestra en un `Banner` de éxito y se dispara `cargarPlanes()`, que llama a `listPlans()` (`GET /plans`) para refrescar el historial — el router lee directamente el directorio `CARPETA_PLANES` con `glob("*.md")` y lo ordena por fecha de modificación, sin tocar ninguna *tool*.
7.
