Agentic System Profile Card — Fase 2

Clemente Reservations & Capacity Agent

Agente conversacional y operativo para gestionar reservas de restaurantes, mantener contexto del cliente, consultar disponibilidad real, proponer alternativas, registrar cambios con trazabilidad y escalar casos especiales al equipo humano.

Proyecto Clemente para Restaurantes
Agente principal Reservas y Capacidad
Autonomía Semi-autónomo con HITL

1. Communication Layer

El agente opera principalmente en conversación digital, pero debe conectarse con eventos operativos internos del restaurante. El canal no es solo chat: cada conversación puede terminar en una acción sobre reservas, mesas, lista de espera o escalamiento.

Canales de cliente

  • WhatsApp para atención principal y confirmaciones.
  • Instagram y Messenger para consultas iniciales.
  • Webchat para reservas desde la web del restaurante.
  • Mensajes de seguimiento previos al día de la visita.

Canales internos

  • Panel del equipo para ver reservas, mesas, solicitudes y estados.
  • Alertas internas cuando el agente no puede resolver un caso.
  • Registro de cambios para auditoría operativa.

Eventos operativos

  • Reserva creada, modificada, cancelada o vencida.
  • Mesa ocupada, liberada o con permanencia alta.
  • Diferencia entre reserva registrada y ocupación real.
  • Feedback posterior a la visita.
WhatsApp Instagram Messenger Webchat Panel interno Eventos de ocupación

2. Context Definition

El contexto del agente se divide en rol, objetivo, estado conversacional, reglas del restaurante, memoria del cliente y resultados de herramientas. La prioridad es que el modelo reciba solo el contexto necesario para decidir la siguiente acción sin saturar el Context Window.

Domain Definition

Clemente Reservations es un agente especializado en reservas, capacidad y atención previa a la visita para restaurantes. No inventa disponibilidad: consulta el sistema operativo antes de prometer una mesa.

  • Domina horarios, zonas, mesas, combinaciones y reglas de reserva.
  • Conserva contexto del cliente para personalizar la atención.
  • Traduce conversación en acciones trazables sobre el sistema.

Objectives Definition

Completar reservas válidas con la menor fricción posible, reduciendo errores manuales y escalando excepciones con el contexto ya organizado.

  • Capturar fecha, hora, cantidad de personas, contacto y preferencias.
  • Consultar disponibilidad real antes de confirmar.
  • Proponer alternativas cuando no haya cupo exacto.
  • Registrar modificación, cancelación o lista de espera con confirmación explícita.

3. Context Engineering

El Context Window se trata como un recurso limitado. El agente no debe cargar toda la operación del restaurante en cada turno; debe construir un paquete contextual mínimo, fresco y verificable.

Componente Contenido que entra al contexto Presupuesto estimado Política
System prompt Rol, límites, criterio de decisión, reglas de no alucinación y escalamiento. 900-1,200 tokens Fijo, versionado como memoria procedimental.
Input actual Mensaje del cliente o evento operativo que dispara el turno. 200-600 tokens Siempre entra completo.
Estado de reserva Fecha, hora, personas, zona, contacto, preferencias, estado y acción pendiente. 300-700 tokens Resumen estructurado, no historial crudo.
Memoria de cliente Preferencias, alergias, historial resumido, no-shows y notas aprobadas. 300-700 tokens Solo datos relevantes para la reserva actual.
RAG operativo Reglas de reserva, horarios, políticas, zonas y condiciones vigentes. k=4 fragmentos, 1,200-1,600 tokens Recuperar por intención; descartar documentos vencidos.
Tool docstrings Descripción mínima de tools disponibles para disponibilidad, reserva y escalamiento. 700-1,000 tokens Docstrings breves, inputs/outputs claros.
Tool results Disponibilidad consultada, alternativas, tabla asignada o error operacional. 500-1,200 tokens Entrar como resultado estructurado, no como texto largo.
Output reservado Respuesta al cliente o resumen para el equipo interno. 400-800 tokens Reservado explícitamente para evitar cortes.

Prompt dinámico por variables

El prompt se renderiza por turno con variables de dominio, usuario, reserva y operación.

agent_name = "Clemente Reservations"
restaurant_profile = {...}
reservation_state = {...}
customer_memory = {...}
retrieved_policy_chunks = [...]
available_tools = [...]
criticality_rules = [...]
pending_human_review = false

Estrategia de contexto

  • Prioridad 1: input actual, estado de reserva y resultados de tools.
  • Prioridad 2: políticas vigentes recuperadas por RAG.
  • Prioridad 3: preferencias e historial resumido del cliente.
  • Recorte: `summary` para conversación larga y `trim_tokens` antes del modelo.
  • No entra: video, logs crudos, políticas antiguas, datos personales no necesarios.
Principio de diseño: disponibilidad, ocupación, mesas y políticas críticas no se infieren desde memoria ni desde lenguaje natural. Se consultan mediante herramientas antes de ofrecer o confirmar una acción.

4. Memory Architecture

La memoria se divide entre estado de conversación, memoria persistente del cliente, conocimiento operativo y aprendizaje limitado por feedback. No toda memoria autoriza acción automática.

Tipo de memoria Qué guarda Persistencia Uso en decisión
Short-term / Working Memory Reserva en construcción, última intención, slots ofrecidos, confirmación pendiente. Checkpointer por `thread_id`. Evitar repetir preguntas y sostener el flujo actual.
Long-term Memory Perfil del cliente, preferencias, alergias, historial de reservas, no-shows. Store por `(restaurant_id, customer_id)`. Personalizar y detectar riesgos operativos.
Episodic Memory Resumen de interacciones pasadas y acciones ejecutadas. Store con eventos auditables. Saber qué ocurrió antes sin cargar conversaciones completas.
Semantic Memory FAQs, reglas de reserva, políticas, horarios, zonas, layout y condiciones vigentes. Base documental/RAG. Responder con grounding y aplicar políticas actualizadas.
Procedural Memory System prompt, prompts dinámicos, tool registry, guardrails, evals y reglas HITL. Versionado en código/configuración. Define cómo debe actuar el agente.
Learning Memory Preferencias confirmadas, patrones de no-show, feedback posterior y señales de satisfacción. Store analítico con aprobación de reglas. Ajustar recomendaciones, no cambiar políticas críticas de forma autónoma.

Estado corto plazo

  • `intent`: crear, modificar, cancelar, consultar.
  • `reservation_draft`: fecha, hora, personas, zona, notas.
  • `missing_fields`: datos faltantes.
  • `offered_slots`: alternativas ya ofrecidas.
  • `pending_confirmation`: acción que requiere sí explícito.

Store largo plazo

  • Namespace: `(restaurant_id, customer_id)`.
  • Separar PII de preferencias operativas.
  • Registrar fuente y fecha de cada dato persistido.
  • Permitir borrado/rectificación de datos del cliente.

Ciclo de memoria

  • Capturar datos durante la conversación.
  • Confirmar antes de persistir datos sensibles.
  • Resumir conversación al cerrar la reserva.
  • Actualizar preferencias solo con evidencia explícita.

5. Reflex Agent Types

El diseño recomendado no usa un único tipo puro. Clemente Reservations es un agente híbrido: combina reglas reflejas para seguridad, estado interno para conversación/capacidad, planificación para completar reservas, utilidad para elegir alternativas y aprendizaje limitado para mejorar personalización.

Tipo reflexivo Uso en Clemente Ejemplo de decisión Nivel de autonomía
Simple Reflex Agent Reglas inmediatas de seguridad, políticas y datos faltantes. Si faltan fecha o cantidad de personas, preguntar antes de consultar disponibilidad. Constrained
Model-Based Reflex Agent Mantiene estado interno de reserva, cliente, mesa, ocupación y conversación. Si el cliente ya eligió `20:30`, no volver a ofrecer `20:30`; pasar a confirmación. Semi-autonomous
Goal-Based Agent Planifica los pasos para completar una reserva válida. Recolectar campos faltantes, consultar cupo, ofrecer slot, confirmar y registrar. Semi-autonomous
Utility-Based Agent Rankea alternativas de horario/mesa según preferencias y operación. Elegir la alternativa con mejor balance entre preferencia del cliente, capacidad y rotación. Semi-autonomous con límites
Learning Agent Aprende preferencias y patrones desde feedback, sin modificar reglas críticas. Recordar que el cliente prefiere terraza y suele llegar 10 minutos tarde. Constrained learning
1. Percepto Mensaje del cliente o evento operativo.
2. Estado Actualizar reserva, cliente y ocupación conocida.
3. Reglas Aplicar políticas simples y bloqueos críticos.
4. Meta Completar reserva o resolver modificación/cancelación.
5. Utilidad Rankear alternativas viables.
6. Acción Responder, registrar, escalar o pedir confirmación.

6. Tools, Actions and Environment Definition

Las tools son actuadores y sensores del agente. Las acciones que cambian estado operativo requieren validación previa y, en algunos casos, confirmación humana.

Tool Tipo Entrada Salida Riesgo Control
`get_restaurant_policy` Conocimiento Intención, fecha, restaurante. Reglas vigentes y fuentes. Bajo Solo lectura.
`check_availability` Sensor operacional Fecha, hora, personas, zona. Slots y mesas disponibles. Medio Consulta tiempo real.
`rank_reservation_options` Utilidad Slots, preferencias, constraints. Opciones rankeadas con score. Medio Fórmula auditable.
`create_reservation_request` Actuador Datos confirmados de reserva. Reserva pendiente/confirmada. Alto Confirmación explícita del cliente.
`modify_reservation` Actuador ID reserva, nuevos datos. Reserva actualizada. Alto Validar disponibilidad y confirmar.
`cancel_reservation` Actuador ID reserva, motivo. Cancelación registrada. Alto Confirmación explícita y política vigente.
`escalate_to_staff` Control/HITL Motivo, resumen, datos capturados. Tarea interna asignada. Medio Resumen trazable.
`save_customer_memory` Memoria Dato, fuente, consentimiento. Preferencia o nota persistida. Medio No persistir datos sensibles sin necesidad.

7. Utility Function for Reservation Options

La utilidad no reemplaza las reglas del restaurante. Primero se filtran opciones inválidas; luego se rankean las alternativas viables.

Restricciones duras

  • No confirmar si `available = false`.
  • No superar capacidad máxima declarada.
  • No ignorar alergias, accesibilidad o notas críticas.
  • No asignar mesas inexistentes ni modificar layout automáticamente.
  • No confirmar cambios/cancelaciones sin consentimiento explícito.

Score de utilidad

U(slot) =
  0.30 * preference_fit
+ 0.25 * capacity_fit
+ 0.20 * operational_efficiency
+ 0.15 * waiting_time_score
+ 0.10 * customer_history_fit
- penalties(no_show_risk, policy_edge_case)
Uso esperado: si el cliente pide 8:00 p. m. y no hay cupo, el agente no responde solo "no hay". Consulta alternativas, las rankea y ofrece dos o tres opciones explicables: horario más cercano, zona preferida disponible o lista de espera.

8. Autonomy, Criticality and HITL

El agente es semi-autónomo: puede consultar, recomendar y preparar acciones, pero las operaciones que afectan una reserva real requieren confirmación explícita del cliente o revisión humana según criticidad.

Puede hacer sin aprobación

  • Responder FAQs con fuentes vigentes.
  • Preguntar por datos faltantes.
  • Consultar disponibilidad.
  • Ofrecer alternativas viables.
  • Preparar resumen de reserva.

Requiere confirmación del cliente

  • Crear una reserva.
  • Modificar fecha, hora, zona o número de personas.
  • Cancelar reserva.
  • Guardar preferencias persistentes no obvias.

Escala a humano

  • Grupos grandes o fuera de capacidad estándar.
  • Alergias severas, accesibilidad o eventos especiales.
  • Conflictos de disponibilidad u overbooking detectado.
  • Cliente molesto o incidencia abierta.
  • Tres intentos fallidos de resolver el flujo.

9. Guardrails and Controls

Los guardrails combinan reglas deterministas, validación contra herramientas, protección de datos y escalamiento. El objetivo es que el agente no prometa lo que el sistema no puede sostener.

Riesgo Control Respuesta esperada
Alucinación de disponibilidad Tool obligatoria `check_availability` antes de ofrecer o confirmar. Si la tool falla, no confirmar; escalar o pedir esperar.
Overbooking Validar capacidad, mesa, zona y combinación en tiempo real. Bloquear creación y ofrecer alternativas.
Datos personales innecesarios Minimización de PII; guardar solo contacto y preferencias útiles. No pedir DNI, datos de pago ni información sensible no requerida.
Alergias o condiciones médicas Marcar como nota crítica y escalar si hay duda. No prometer seguridad alimentaria absoluta.
Uso de visión computacional Procesar eventos operativos, no identificación individual persistente. Usar señales como `mesa_liberada`; no reconocimiento facial.
Memoria incorrecta Guardar fuente, fecha y permitir corrección. Confirmar preferencias antes de persistirlas.
Acción irreversible HITL o confirmación explícita según criticidad. El agente prepara la acción, pero no la ejecuta sin aprobación.

10. Evals and Observability

La evaluación debe medir trayectorias completas, no solo respuestas finales. El agente puede sonar correcto y aun así haber consultado mal disponibilidad, omitido una confirmación o guardado memoria indebida.

Evals funcionales

  • Completa reserva con todos los campos obligatorios.
  • No confirma sin disponibilidad real.
  • Propone alternativas cuando el horario pedido no existe.
  • Escala grupos grandes y casos especiales.

Evals de memoria

  • No pierde fecha, hora ni cantidad durante el flujo.
  • No usa preferencias de otro cliente.
  • No persiste datos sensibles sin necesidad.
  • Actualiza preferencias solo con evidencia explícita.

Métricas operativas

  • Tasa de conversión consulta-reserva.
  • Tiempo promedio hasta confirmación.
  • Tasa de overbooking: objetivo 0.
  • Tasa de escalamiento y motivo.
  • Utility regret en opciones recomendadas.
Observabilidad mínima: registrar `input -> estado -> tool calls -> resultado -> respuesta -> acción final`. Ese rastro permite auditar por qué el agente ofreció un horario, por qué escaló o por qué bloqueó una reserva.
