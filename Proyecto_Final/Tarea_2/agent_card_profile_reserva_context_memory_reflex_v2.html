Agent Profile Card — Fase 2 corregida

Clemente Reservations

Agente para reservas de restaurantes que mantiene contexto de la conversación, consulta disponibilidad real, guía al cliente hasta una reserva confirmada y recomienda alternativas cuando el horario pedido no está libre.

Proyecto Clemente para Restaurantes
Memoria aplicada Short-term + Long-term
Agentes adecuados Model-Based, Goal-Based, Utility-Based
Descartados Simple Reflex y Learning

1. Communication Layer

El agente continúa una conversación ya iniciada con el cliente y la convierte en una acción operativa: consultar disponibilidad, proponer alternativas, confirmar reserva o escalar al staff.

Canales conversacionales

  • WhatsApp como canal principal de atención y confirmación.
  • Instagram, Messenger y Webchat para consultas iniciales.
  • Seguimiento previo al día de la visita.

Interacción con operación

  • Consulta disponibilidad antes de prometer una mesa.
  • Registra reserva solo después de confirmación explícita.
  • Escala grupos grandes, alergias críticas o conflictos de capacidad.

2. Context Engineering

El Context Window se arma con lo estrictamente útil para resolver el turno: mensaje actual, borrador de reserva, perfil relevante del cliente, reglas vigentes y resultados de herramientas. No se cargan todos los documentos ni todo el historial crudo.

Componente Qué entra al contexto Por qué entra Política
System prompt Rol del agente, límites, reglas de confirmación y escalamiento. Define el comportamiento procedimental del agente. Fijo y versionado.
Mensaje actual Última intención o respuesta del cliente. Es el percepto principal del turno. Siempre completo.
Borrador de reserva Fecha, hora, personas, zona, ocasión, notas y datos faltantes. Modelo interno necesario para no repetir preguntas. Resumen estructurado.
Perfil relevante Nombre, teléfono, preferencias, alergias y zona favorita si existen. Personaliza y reduce fricción. Solo datos relevantes; no PII innecesaria.
Reglas operativas Horarios, políticas de reserva, cancelación, grupos y alergias. Evita respuestas desactualizadas o fuera de política. Recuperar solo reglas relacionadas con la intención.
Resultados de tools Disponibilidad consultada, alternativas y estado de reserva. Grounding operativo para decidir. JSON/resumen estructurado, no texto extenso.

Prompt dinámico esperado

system_prompt(
  restaurant_rules,
  customer_profile,
  reservation_draft,
  availability_checked,
  pending_confirmation
)

Estrategia de recorte

  • Historial crudo solo mientras sea corto.
  • Cuando crece, reemplazar por resumen del estado de reserva.
  • No cargar conversaciones antiguas completas.
  • El resultado más reciente de disponibilidad tiene prioridad sobre memoria.

3. Uso de Memoria Seleccionado

Para este proyecto sí aplican memoria de corto plazo y memoria de largo plazo. No se declaran como componentes aplicados la memoria episódica, semántica, procedimental ni learning memory, porque el Profile Card original y el README de referencia no las piden como entregable actual.

Memoria Qué guarda Uso en Clemente Implementación sugerida
Short-term Memory Datos de la reserva actual: fecha, hora, personas, zona, ocasión, notas, opción elegida y confirmación pendiente. Permite continuar la conversación sin pedir otra vez datos ya entregados. Historial de mensajes + `borrador_reserva` en estado de conversación.
Long-term Memory Nombre, teléfono, preferencias, alergias, zona favorita e historial de reservas. Personaliza recomendaciones y ayuda a detectar notas críticas. Store por teléfono o `customer_id`, validando consentimiento para datos sensibles.
No se fuerza Learning Agent: guardar preferencias no es lo mismo que aprendizaje por refuerzo. Para declarar Learning faltaría un crítico o señal de feedback definida, por ejemplo no-show, cancelación, corrección del staff o satisfacción posterior.

4. Tipos de Agentes Reflexivos Adecuados

Siguiendo el README de referencia, el diseño correcto no aplica los cinco tipos de IBM. Se seleccionan tres porque corresponden directamente a lo que el Profile Card exige: memoria, meta y recomendación entre opciones.

Tipo IBM Estado Por qué aplica o no aplica Sección del Profile Card que resuelve
Model-Based Reflex Agent Seleccionado El agente necesita un modelo interno: perfil del cliente, borrador de reserva y disponibilidad ya consultada. Environment Definition: Long/Short Term Memory. Communication Layer: continúa conversación iniciada.
Goal-Based Agent Seleccionado El agente persigue una meta concreta: reserva confirmada o escalamiento controlado. Autonomy Dimension: guía la reserva y escala casos especiales.
Utility-Based Agent Seleccionado Cuando hay varias franjas válidas, debe recomendar una según horario, zona y ajuste de capacidad. Objectives Definition: ofrecer franjas disponibles. Autonomy: recomienda horarios.
Simple Reflex Agent Descartado No alcanza como arquitectura base porque no tiene memoria y el Profile Card exige memoria explícita. Solo puede aparecer como regla interna de guardrail, no como tipo de agente principal.
Learning Agent Descartado por ahora No hay crítico ni loop de feedback definido en el Profile Card actual. Evolución futura si se registra feedback real: no-shows, cancelaciones, correcciones del staff.

5. Orquestación Propuesta

Los tres tipos seleccionados no compiten: se coordinan dentro del flujo de reserva. El agente basado en modelo mantiene estado, el basado en objetivos guía el avance, y el basado en utilidad ordena alternativas cuando hay varias opciones disponibles.

1. Model-Based

  • Actualiza `perfil_cliente`.
  • Actualiza `borrador_reserva`.
  • Recuerda disponibilidad ya consultada.
  • Evita repetir preguntas.

2. Goal-Based

  • Identifica datos faltantes.
  • Busca disponibilidad.
  • Pide confirmación explícita.
  • Confirma o escala.

3. Utility-Based

  • Evalúa franjas disponibles.
  • Considera zona favorita.
  • Evita uso ineficiente de mesas.
  • Explica el trade-off.

6. Autonomía, Criticidad y Controles

El agente es semi-autónomo. Puede conversar, consultar y recomendar; pero crear, modificar o cancelar una reserva exige confirmación explícita. Casos especiales se escalan al staff.

Puede hacer solo

  • Preguntar datos faltantes.
  • Consultar disponibilidad.
  • Ofrecer alternativas.
  • Preparar resumen de reserva.

Requiere confirmación

  • Crear reserva.
  • Modificar reserva.
  • Cancelar reserva.
  • Guardar preferencias persistentes.

Escala al staff

  • Grupos grandes.
  • Alergias severas.
  • Eventos privados.
  • Conflictos de disponibilidad.
  • Varios intentos fallidos.

7. Tools para la Implementación en LangChain

La implementación debe reflejar los tres tipos seleccionados, no una lista completa de todos los tipos de la clase.

Tool Agente asociado Función Guardrail
`actualizar_borrador_reserva` Model-Based Actualiza memoria corta de la reserva en curso. No inventar campos faltantes.
`verificar_disponibilidad` Model-Based / Goal-Based Consulta si el horario y mesa son viables. Obligatoria antes de ofrecer o confirmar.
`buscar_alternativas_disponibles` Goal-Based Replanifica si el horario solicitado no está libre. Máximo tres opciones al cliente.
`confirmar_reserva` Goal-Based Registra la reserva cuando ya existe confirmación explícita. No ejecutar sin resumen y confirmación.
`evaluar_opcion_reserva` Utility-Based Calcula score de horario, zona y ajuste de capacidad. Función de utilidad auditable.
`escalar_a_staff` Goal-Based Crea una tarea interna cuando la meta no puede alcanzarse automáticamente. Usar en casos críticos o tras fallos repetidos.
