Agent Profile Card — Fase 2 · v3

Clemente Reservations

Agente para reservas de restaurantes que mantiene contexto de la conversación, consulta disponibilidad real, guía al cliente hasta una reserva confirmada y recomienda alternativas cuando el horario pedido no está libre. Esta versión completa el presupuesto de Context Window y la arquitectura de memoria (CoALA) que la v2 había simplificado, y agrega el agente unificado de producto (04) al inventario de implementación.

Proyecto Clemente para Restaurantes
Memoria aplicada Short-term + Long-term (primarias)
Agentes seleccionados Model-Based, Goal-Based, Utility-Based
Descartados (con justificación) Simple Reflex y Learning

1. Communication Layer

El agente continúa una conversación ya iniciada con el cliente y la convierte en una acción operativa: consultar disponibilidad, proponer alternativas, confirmar reserva o escalar al staff.

Canales conversacionales

  • WhatsApp como canal principal de atención y confirmación.
  • Instagram, Messenger y Webchat para consultas iniciales.
  • Seguimiento previo al día de la visita.

Interacción con operación

  • Consulta disponibilidad antes de prometer una mesa.
  • Registra reserva solo después de confirmación explícita.
  • Escala grupos grandes, alergias críticas o conflictos de capacidad.

2. Context Engineering — presupuesto de Context Window

El Context Window se trata como recurso escaso (Sesión 9, §2-3): system prompt, input, historial, tool docstrings y resultados de tools compiten por el mismo espacio. Modelo de referencia para el laboratorio: ollama:llama3.2 (ventana 128K tokens); en la implementación con Anthropic se usa claude-sonnet-4-6.

Componente Qué entra al contexto Presupuesto estimado Política
System prompt Rol del agente, límites, reglas de confirmación y escalamiento. ~900-1,200 tokens Fijo y versionado (memoria procedimental).
Mensaje actual Última intención o respuesta del cliente. ~200-600 tokens Siempre completo.
Borrador de reserva Fecha, hora, personas, zona, ocasión, notas y datos faltantes. ~300-700 tokens Resumen estructurado, no historial crudo.
Perfil relevante Nombre, teléfono, preferencias, alergias y zona favorita si existen. ~300-700 tokens Solo datos relevantes; no PII innecesaria.
Reglas operativas (RAG) Horarios, políticas de reserva, cancelación, grupos y alergias. k=4 fragmentos, ~1,200-1,600 tokens Recuperar solo reglas relacionadas con la intención.
Tool docstrings Descripción de cada tool disponible (disponibilidad, reserva, escalamiento). ~700-1,000 tokens Docstrings breves, un guardrail de negocio por tool.
Resultados de tools Disponibilidad consultada, alternativas y estado de reserva. ~500-1,200 tokens JSON/resumen estructurado, no texto extenso.
Output reservado Respuesta al cliente o resumen para el equipo interno. ~400-800 tokens Reservado explícitamente para evitar cortes.

Prompt dinámico esperado

system_prompt(
  restaurant_rules,
  customer_profile,
  reservation_draft,
  availability_checked,
  pending_confirmation
)

Estrategia de corto plazo (LangGraph memory_strategy)

  • full mientras la conversación es corta (pocos turnos).
  • summary: al crecer, condensar turnos antiguos en un resumen del estado de reserva y descartar el texto crudo.
  • trim_tokens: recorte por presupuesto real de tokens justo antes de invocar al modelo, no por conteo de mensajes.
  • El resultado más reciente de check_availability siempre tiene prioridad sobre memoria vieja (el mundo puede haber cambiado).

3. Arquitectura de Memoria (CoALA)

Siguiendo el framework de las cinco memorias visto en la Sesión 9 (episódica, semántica, procedimental, largo plazo, corto plazo), esta versión declara el estado de las cinco en vez de omitir las que no son primarias. Short-term y Long-term son las memorias primarias del agente — las que sostienen el flujo de reserva; las otras tres existen de forma más ligera o quedan como roadmap explícito.

Memoria (CoALA) Qué guarda en Clemente Estado Implementación
Short-term / Working Memory Datos de la reserva actual: fecha, hora, personas, zona, ocasión, notas, opción elegida y confirmación pendiente. Primaria — aplicada Historial de mensajes + borrador_reserva en el estado del grafo (ClementeState).
Long-term Memory Nombre, teléfono, preferencias, alergias, zona favorita e historial de reservas. Primaria — aplicada Store por teléfono/customer_id (perfil_cliente), validando consentimiento para datos sensibles.
Procedural Memory Estructura del system prompt / dynamic_prompt, registro de tools disponibles y guardrails. Aplicada implícitamente Vive como código versionado (los propios scripts 01-04); no hay un Prompt/Tool Registry externo todavía.
Semantic Memory FAQs, políticas de reserva/cancelación, horarios y reglas de zonas. Aplicada de forma mínima Hoy vive como diccionarios en memoria (MESAS, TURNOS_VALIDOS, políticas); roadmap: migrar a base vectorial + get_restaurant_policy con RAG real.
Episodic Memory Interacciones y acciones pasadas del agente (qué se ofreció, qué se confirmó, qué se escaló). No aplicada — roadmap Requiere instrumentar un log de eventos auditable por reserva; hoy solo vive en el historial de mensajes de la sesión activa.
No se fuerza Learning Agent: guardar preferencias (long-term) no es lo mismo que aprendizaje por refuerzo. Para declarar Learning faltaría un crítico o señal de feedback definida — por ejemplo no-show, cancelación, corrección del staff o satisfacción posterior — que hoy el sistema de reservas real no emite.

4. Tipos de Agentes Reflexivos Adecuados

Siguiendo el README de referencia, el diseño correcto no aplica los cinco tipos de IBM. Se seleccionan tres porque corresponden directamente a lo que el Profile Card exige: memoria, meta y recomendación entre opciones. Simple Reflex y Learning quedan fuera de la arquitectura base, pero documentados con su justificación —no omitidos— para que la elección sea auditable frente a la rúbrica de la Sesión 10.

Tipo IBM Estado Por qué aplica o no aplica Sección del Profile Card que resuelve
Model-Based Reflex Agent Seleccionado El agente necesita un modelo interno: perfil del cliente, borrador de reserva y disponibilidad ya consultada. Environment Definition: Long/Short Term Memory. Communication Layer: continúa conversación iniciada.
Goal-Based Agent Seleccionado El agente persigue una meta concreta: reserva confirmada o escalamiento controlado. Autonomy Dimension: guía la reserva y escala casos especiales.
Utility-Based Agent Seleccionado Cuando hay varias franjas válidas, debe recomendar una según horario, zona y ajuste de capacidad. Objectives Definition: ofrecer franjas disponibles. Autonomy: recomienda horarios.
Simple Reflex Agent Descartado como arquitectura base No alcanza solo, porque el Profile Card exige memoria explícita. El patrón condición-acción sigue vivo dentro de los otros 3 agentes como guardrail (ej. "sin confirmación explícita → no registrar"). Presente como regla interna, no como tipo de agente principal.
Learning Agent Descartado por ahora No hay crítico ni loop de feedback definido en el Profile Card actual (no-show, cancelación, corrección del staff). Evolución futura: reutilizar evaluar_opcion_reserva/rank_reservation_options con un store de confianza histórico, mismo patrón que 05_learning_agent.py de /Examples.

5. Orquestación Propuesta e Inventario de Implementación

Los tres tipos seleccionados no compiten: se coordinan dentro del flujo de reserva. Existen dos niveles de implementación en Python: los tres agentes aislados (didácticos, un tipo por archivo) y un cuarto agente que los une en un solo flujo de producto.

1. Model-Based

  • Actualiza perfil_cliente.
  • Actualiza borrador_reserva.
  • Recuerda disponibilidad ya consultada.
  • Evita repetir preguntas.

2. Goal-Based

  • Identifica datos faltantes.
  • Busca disponibilidad.
  • Pide confirmación explícita.
  • Confirma o escala.

3. Utility-Based

  • Evalúa franjas disponibles.
  • Considera zona favorita.
  • Evita uso ineficiente de mesas.
  • Explica el trade-off.

4. Unified (nuevo)

  • Colapsa 1+2+3 en un solo agente.
  • Utilidad con fallback (cliente nuevo vs. conocido).
  • Cierra el flujo: confirma y escala.
  • Es el agente de producto; 01-03 quedan como material didáctico.
Inventario en pruebas/Agente_Reservas/: 01_model_based_reflex_agent.py, 02_goal_based_agent.py, 03_utility_based_agent.py y 04_unified_agent.py (nuevo, aporte de equipo adaptado a esta card). Existe además un prototipo alterno independiente, Tarea_2/agente_reservas_clemente_langchain.py, con Anthropic + persistencia JSON/JSONL y el set completo de tools de producto — se documenta como referencia, no como entregable canónico de esta fase.

6. Autonomía, Criticidad y Controles

El agente es semi-autónomo. Puede conversar, consultar y recomendar; pero crear, modificar o cancelar una reserva exige confirmación explícita. Casos especiales se escalan al staff.

Puede hacer solo

  • Preguntar datos faltantes.
  • Consultar disponibilidad.
  • Ofrecer alternativas.
  • Preparar resumen de reserva.

Requiere confirmación

  • Crear reserva.
  • Modificar reserva.
  • Cancelar reserva.
  • Guardar preferencias persistentes.

Escala al staff

  • Grupos grandes.
  • Alergias severas.
  • Eventos privados.
  • Conflictos de disponibilidad.
  • Varios intentos fallidos.

7. Tools para la Implementación en LangChain

La implementación debe reflejar los tres tipos seleccionados, no una lista completa de todos los tipos de la clase.

Tool Agente asociado Función Guardrail
consultar_perfil_cliente Model-Based Carga long-term memory del cliente por teléfono. Llamar al inicio de la conversación, no inventar historial.
actualizar_borrador_reserva Model-Based Actualiza memoria corta de la reserva en curso. No inventar campos faltantes.
verificar_disponibilidad Model-Based / Goal-Based Consulta si el horario y mesa son viables. Obligatoria antes de ofrecer o confirmar.
buscar_alternativas_disponibles Goal-Based Replanifica si el horario solicitado no está libre. Máximo tres opciones al cliente.
confirmar_reserva / registrar_reserva_pendiente Goal-Based Registra la reserva cuando ya existe confirmación explícita. No ejecutar sin resumen y confirmación.
evaluar_opcion_reserva Utility-Based Calcula score de horario, zona y ajuste de capacidad. Función de utilidad auditable, pesos configurables.
escalar_a_staff Goal-Based (transversal) Crea una tarea interna cuando la meta no puede alcanzarse automáticamente. Usar en casos críticos o tras fallos repetidos.
